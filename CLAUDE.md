# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

.NET 10 solution (`CqrsApiExample.slnx`; SDK pinned to 10.0.x by `global.json`). Run from the repo root:

```bash
dotnet tool restore                                 # once: installs the repo-local dotnet-ef
dotnet build CqrsApiExample.slnx
dotnet test CqrsApiExample.slnx                     # integration tests need Docker (Testcontainers)
docker compose up --build                           # SQL Server + API in containers: http://localhost:5235 (/swagger)
docker compose up db                                # only SQL Server; then run the API locally:
dotnet run --project src/Api          # http://localhost:5235; Development: /swagger UI, /openapi/v1.json

# Single test / subset (xUnit)
dotnet test tests/Domain.UnitTests                 # one test project
dotnet test --filter "FullyQualifiedName~UsersEndpointsTests.GetUser_Returns_404_When_User_Does_Not_Exist"
dotnet test --filter "Category=Architecture"       # tests are tagged with [Trait("Category", ...)]

# Formatting (.editorconfig): fix, or check without changing files
dotnet format CqrsApiExample.slnx
dotnet format CqrsApiExample.slnx --verify-no-changes

# Benchmarks: EF Core vs ADO.NET (Release; starts its own SQL Server container, so Docker is required)
dotnet run -c Release --project benchmarks/Persistence.Benchmarks
dotnet run -c Release --project benchmarks/Persistence.Benchmarks -- --filter *Read*   # a subset

# EF Core migrations (they live in CqrsApiExample.Infrastructure; the API is the startup project)
dotnet ef migrations add <Name> --project src/Infrastructure --startup-project src/Api --output-dir Persistence/Migrations
```

`_requests/users.rest` has ready-made HTTP requests (VS Code REST Client) against `http://localhost:5235/api`, including the duplicate-email and validation-error cases.

The database is **SQL Server** (EF Core SqlServer provider, connection string `ConnectionStrings:Database`). `appsettings.json` has no connection string on purpose, so production must provide it (for example `ConnectionStrings__Database`). `appsettings.Development.json` points to the compose container on `127.0.0.1,14330` (not `localhost`: it resolves to `::1` first, and the port is published on IPv4 only, so clients time out) with a local-only SA password; `MSSQL_SA_PASSWORD` overrides it in compose. In Development, `Program.cs` calls `app.Services.InitialiseDatabaseAsync()` (`Infrastructure/Data/DbInitializer.cs`), which applies pending migrations and seeds one user (`jane.doe@example.com`, password `DbInitializer.SeedUserPassword`). Outside Development nothing is applied automatically: use a migration bundle or script as a deployment step. After changing an entity or a `*Configuration.cs`, add a migration; don't go back to `EnsureCreated`.

Docker: `Dockerfile` (multi-stage; restores from the csproj files first for layer caching; runs as the non-root `$APP_UID` on port 8080) and `compose.yaml` (`db`: `mssql/server:2022-latest`, healthcheck, volume `mssql-data`; `api`: Development environment, starts after the db is healthy). Ports bind to `127.0.0.1` only. The developer has several projects, each with its own SQL Server, so this one must stay distinguishable. It uses host port **14330** (not 1433, overridable with `MSSQL_HOST_PORT`), container and server name **`cqrs-api-example-sql`** (`@@SERVERNAME` / `SERVERPROPERTY('MachineName')`), database **`CqrsApi`**, and the SQLTools connection in `.vscode/settings.json` is in group `CqrsApiExample`. If the port changes, update `compose.yaml`, `appsettings.Development.json` and `.vscode/settings.json` together. The SA password is saved in `.vscode/settings.json` on purpose (local-only, the developer asked for it). SQL Server has no ARM image, so on Apple Silicon it runs emulated (`platform: linux/amd64`) and starts more slowly.

## Architecture

Clean Architecture + CQRS, with no mediator library (MediatR was removed in stage 13). Projects and namespaces are named `CqrsApiExample.<Layer>`, but their folders omit the prefix (`src/Domain/CqrsApiExample.Domain.csproj`, `tests/Domain.UnitTests/...`). Project dependencies point inward:

- **CqrsApiExample.Domain**: persistence-ignorant and package-free (no EF, no DataAnnotations, no NuGet packages). `Entity` generates its own `Id` (Guid v7) and compares by identity. Aggregates such as `User` have private setters and are created through a factory (`User.Create`) that enforces invariants and returns `Result<T>`. `CreatedAt`/`ModifiedAt` have private setters and are filled by `AuditableEntityInterceptor` in Infrastructure. EF mapping lives in `Infrastructure/Persistence/Configurations/*Configuration.cs`, which reuses the max-length constants defined on the entity. `Common/Results` holds the project's own `Result<T>`/`Error`/`ErrorType`, which all layers use. `User` stores only a `PasswordHash` (`User.Create(name, surname, email, passwordHash)` throws on an empty hash: a missing hash is a caller bug, not input); the password rules (`PasswordMinLength`/`PasswordMaxLength`) live on `User` but only the validator applies them. Use `User.NormalizeEmail` wherever a user is looked up by email. Domain errors are `Error` values in the partial static class `Errors` (`Errors.Users.*`, `Errors.Auth.*`, `Errors.Generic.*`), one file per area.
- **CqrsApiExample.Application**: organized by feature: `Users/Commands/<Name>/`, `Auth/Commands/Login/`, `Users/Queries/<Name>/`, `Users/Events/` (domain event handlers). Each command/query folder holds the request (a `sealed record` implementing `ICommand<Result<T>>` or `IQuery<Result<T>>`), its handler (`IRequestHandler<TRequest, Result<T>>`), and an optional FluentValidation validator. The messaging contracts are the project's own, in `Common/Messaging/` (`IRequest`, `ICommand`, `IQuery`, `IRequestHandler`, one file each). Commands and queries return read models (`Users/UserDto.cs`), never domain entities. `Common/` holds persistence, notification and authentication abstractions (`Interfaces/Persistence`, `Interfaces/Notifications`, `Interfaces/Authentication`: `IPasswordHasher`, `IAccessTokenIssuer`), application exceptions (`Exceptions`), the domain-event plumbing (`Events`) and the handler decorators (`Decorators`).
- **CqrsApiExample.Infrastructure**: EF Core `ApplicationDbContext`, `UnitOfWork`, plus two separate kinds of data access:
  - **Write side**: `Persistence/Repositories/UserRepository` implements `IUserRepository`. It loads and tracks aggregates, exposes only what commands use, and never calls `SaveChanges`. Command handlers commit explicitly with `IUnitOfWork.SaveChangesAsync`.
  - **Read side**: `Persistence/Queries/UserQueries` implements `IUserQueries`. It uses `AsNoTracking()` and projects straight to `UserDto` with `Select`, so it skips aggregates and the change tracker. Query handlers depend only on `I*Queries`, never on repositories.
  - `UnitOfWork` translates provider errors (SQL Server unique violations: `SqlException.Number` 2601 for a unique index, 2627 for a unique constraint) into `UniqueConstraintViolationException`, defined in the Application so it doesn't depend on EF (the error numbers live in `Persistence/SqlServerErrors`, shared by both providers). Implementation classes are `internal`; `InternalsVisibleTo` exposes them to CqrsApiExample.Infrastructure.IntegrationTests.
  - **Two providers, one flag.** `Persistence:Provider` (`Ado` or `EfCore`; `appsettings.json` and compose select `Ado`, and the code falls back to `EfCore` only when no value is configured; env `Persistence__Provider`, compose `PERSISTENCE_PROVIDER=EfCore docker compose up`) picks the implementation behind `IUserRepository`/`IUnitOfWork`/`IUserQueries`. It is read lazily when the services resolve (`ValidateOnStart`), and an unknown value fails with a clear message. `Persistence/Ado/` is plain ADO.NET (Microsoft.Data.SqlClient, hand-written SQL with explicit `SqlDbType`; always `DateTime2` for dates). `AdoChangeSet` (scoped) is its minimal change tracker: the repository adds to it, and `AdoUnitOfWork` inserts the aggregates and their outbox rows in one transaction, so the outbox guarantee is the same as with EF. `AdoWriteMode` (optional constructor parameter) has two modes. `Batched` is the default and what DI uses: one command `SET XACT_ABORT ON; BEGIN TRAN; INSERT…; COMMIT`, one round trip, like EF's command batching. **`XACT_ABORT ON` is required**: without it a unique violation only ends that INSERT and the COMMIT stores an orphan outbox row (a test fails if it is removed). `CommandPerStatement` uses a client-side transaction and one command per INSERT (BEGIN, each INSERT and COMMIT are separate round trips); it exists to measure what batching saves. Parameter names carry a per-statement prefix (`a0_`, `m0_`), and a command takes at most 2100 parameters (about 175 users with their events). It sets `CreatedAt` by reflection (`AuditFields`), the job the EF interceptor does, and only supports inserts today (a new aggregate needs a case in `AdoUnitOfWork.Insert`). `AdoRetry` mirrors `EnableRetryOnFailure` (3 retries, at most 5 s apart) and retries the whole unit, never a command inside a transaction. The EF migrations own the schema for both, and `OutboxProcessor`/`DbInitializer` always use EF.
  - **Persistence metrics.** `AddPersistence` wraps whichever provider is configured in the `Persistence/Decorators` (`UserRepositoryInstrumentationDecorator`, `UserQueriesInstrumentationDecorator`, `UnitOfWorkInstrumentationDecorator`), which call `Persistence/Instrumentation/PersistenceInstrumentation`, so both are measured the same way. Each call logs `Persistence <Provider> <Operation> <succeeded|failed|cancelled> in <ms> ms` (Information, without the exception, which the global handler logs) and records it in the histogram `cqrsapi.persistence.operation.duration` of the meter `CqrsApiExample.Persistence`, tagged `provider`/`operation`/`outcome` (`dotnet-counters monitor -n CqrsApiExample.Api --counters CqrsApiExample.Persistence`). A new persistence interface needs both implementations and a decorator.
  - **Benchmarks** (`benchmarks/Persistence.Benchmarks`, BenchmarkDotNet): call the EF Core and ADO.NET implementations directly, without HTTP or the instrumentation decorators. `ReadBenchmarks` covers GetAll/GetById/ExistsByEmail on 100 seeded users. `WriteBenchmarks` covers Add + SaveChanges with the outbox row (EF Core and both `AdoWriteMode`s), in a separate database so the inserts don't change the reads. EF gets a new `DbContext` per call (as per request) with the same retry and interceptor as `AddPersistence`. They run in-process (`InProcessEmitToolchain`), sharing the database prepared in `Program.cs`. BenchmarkDotNet's generated child projects would inherit the strict `Directory.Build.props`. `BENCHMARK_CONNECTION_STRING` uses an existing server instead of a container; its two `PersistenceBenchmarks_*` databases are dropped and recreated every run. Results go to `BenchmarkDotNet.Artifacts/results/*-report-github.md` (gitignored). The project is in the solution but isn't a test project; `InternalsVisibleTo` exposes the Infrastructure internals to it.
- **CqrsApiExample.Contracts**: request and response DTOs for the API surface.
- **Authentication** (`Infrastructure/Authentication`): `Pbkdf2PasswordHasher` (PBKDF2-HMAC-SHA512, 210,000 iterations, BCL only, self-describing `PBKDF2-SHA512.<iterations>.<salt>.<hash>` so the cost can be raised later; `Verify(password, null)` burns the same time against a dummy hash) and `JwtAccessTokenIssuer` (HS256 via `JsonWebTokenHandler`, claims `sub` and `jti` only, times from `TimeProvider`). `JwtOptions` (section `Jwt`: `Issuer`, `Audience`, `SigningKey`, `AccessTokenLifetime`) is public because the API validates tokens with the same values; it is bound lazily and checked with `ValidateOnStart` (the key needs 32+ bytes). `appsettings.json` has no `SigningKey` on purpose; `appsettings.Development.json` has a local-only one. The Infrastructure must not reference ASP.NET Core (architecture test), which is why there is no Identity package.
- **CqrsApiExample.Api**: ASP.NET Core controllers. `Program.cs` wires the layers with `AddPresentation().AddApplication().AddInfrastructure().AddPersistence(config)`; each layer has its own `DependencyInjection.cs`.

### Request flow and error handling

1. A controller (which inherits `ApiControllerBase`) builds a command or query from the contract and calls the handler it receives as an action parameter: `[FromServices] IRequestHandler<TRequest, Result<T>> handler`. There is no mediator, so each action's dependency is explicit. Results (`UserDto`) are converted to contracts with the extension methods in `Api/Common/Mapping/*Mappings.cs` (for example `ToResponse()`). The API project never touches domain entities.
2. The handler a caller receives is wrapped in decorators: `LoggingDecorator` → `ValidationDecorator` → the handler. `AddApplication` (`AddRequestHandlers`) finds every `IRequestHandler<,>` by assembly scanning and builds the closed decorator types **at startup**, so a handler that breaks their constraints fails when the app starts. To add a cross-cutting concern, write another decorator and add it to `decoratorsInnermostFirst`. `LoggingDecorator` logs the elapsed time, and the error codes as a Warning when the `Result` failed. It deliberately doesn't log the request payload (personal data) or exceptions (those are logged by the global handler). `ValidationDecorator` runs the matching `IValidator<TRequest>` if one exists. On failure it returns the errors through `TResponse.Failure(errors)` (a static abstract member of `IFailureResult<TSelf>`, with no exception and no `dynamic`). So **every request's response type must be `Result<T>`**.
3. Handlers return `Result<T>`. Implicit conversions let them `return value;`, `return error;` or `return listOfErrors;`, and `Value` throws on a failed result. **Expected** failures (validation, not found, conflict, an already-translated `UniqueConstraintViolationException`) are returned as errors. **Unexpected** exceptions are never caught in handlers: they propagate to `GlobalExceptionHandler` (`Api/Common/Errors`). That handler logs them once with the stack trace and writes a 500 ProblemDetails (`type`/`errorCodes` = `General.Unexpected`, with `detail` only in Development). A client-cancelled request gets 499 and an Information log. `CancellationToken` flows from the controller action to the EF calls.
4. **Domain events go through a transactional outbox.** Aggregates raise events (`RaiseDomainEvent`, for example `UserCreatedDomainEvent` in `User.Create`). Command handlers never publish anything. `UnitOfWork.SaveChangesAsync` serializes the events of the tracked aggregates into `OutboxMessages` rows **in the same `SaveChanges`/transaction** as the changes, so they exist if and only if the changes were committed. `OutboxBackgroundService` (a hosted service) runs `OutboxProcessor` in a loop. It leases a batch with one `UPDATE … OUTPUT` (`UPDLOCK, READPAST`, so several API instances never share a message and no transaction stays open while handlers run), then runs each handler through `IDomainEventDispatcher` (Application). Each finished handler is recorded in `OutboxMessageConsumers`, so a retry only reruns the handlers that failed. Failures retry with exponential backoff (`OutboxOptions`: 5 s doubling up to 10 min, 10 attempts). After that the message stays with its `Error` (dead letter) and an Error is logged. Delivery is **at-least-once**: a handler can run twice if the process stops right after it, so handlers must tolerate repeats. To react to an event, implement `IDomainEventHandler<TEvent>` (assembly scanning registers it; see `Users/Events/SendWelcomeEmailWhenUserCreated`).
   - Event types are stored by full name and resolved only from the domain assembly (`OutboxSerializer`). Renaming, moving or reshaping an event breaks pending messages, so treat events as a contract. A handler's identity is its type's full name, so renaming a handler makes pending retries run it again.
   - Processed outbox rows are not cleaned up yet. Add a retention job if the table grows.
   - **Authentication happens before any of this.** `AddPresentation` registers JWT bearer validation (`MapInboundClaims = false`, so the user id is the `sub` claim; only HS256; 30 s clock skew) and a **fallback authorization policy** that requires an authenticated user on every endpoint without `[AllowAnonymous]`. Anonymous today: `POST /api/users` (registration), `POST /api/auth/login` and `MapOpenApi().AllowAnonymous()`. An architecture test requires every action (or its controller) to carry `[Authorize]` or `[AllowAnonymous]`. A request without a valid token never reaches the controller: the 401 is empty, and `UseStatusCodePages` turns it into ProblemDetails `Request.Unauthorized` (the `WWW-Authenticate` header says why). Because of the fallback policy, an anonymous request to an unknown route or wrong method also gets 401, not 404/405. `LoginCommand` returns the same `Auth.InvalidCredentials` (401) for an unknown email and a wrong password. Login reads the hash through `IUserQueries.GetCredentialsByEmailAsync` (a `UserCredentialsDto`, never `UserDto`). Commands carrying a password override the record's `PrintMembers` so `ToString` shows `Password = ***`. There are no refresh tokens: a JWT can't be revoked, so keep `AccessTokenLifetime` short.
5. The controller runs `result.Match(ok => ..., errors => Problem(errors))`. `ApiControllerBase.Problem` maps `ErrorType` to a status code (Validation→400 ValidationProblem, Unauthorized→401, Forbidden→403, NotFound→404, Conflict→409, otherwise 500). It also stores the errors in `HttpContext.Items`, so `CqrsApiExampleProblemDetailsFactory` can add `errorCodes` and `traceId` to the ProblemDetails.

### Things that aren't obvious

- EF Core's own failure logs (`SaveChangesFailed`, `QueryIterationFailed`, `CommandError`) are lowered to Debug in `AddPersistence`, because every failure is either translated by `UnitOfWork` or logged by `GlobalExceptionHandler`. Don't log exceptions in handlers or decorators either: one `fail:` per unexpected error is the goal.
- Naming trap: a namespace segment called `Errors` (such as `CqrsApiExample.Api.Common.Errors`) hides the domain class `CqrsApiExample.Domain.Common.DomainErrors.Errors`. Inside such a namespace use `using DomainErrors = CqrsApiExample.Domain.Common.DomainErrors.Errors;`, and don't name new folders `Errors`.
- **Decorator naming.** Every decorator lives in a `Decorators` folder and ends in `Decorator`, so you know where to look and that it is registered as a wrapper of the interface it implements. Generic ones are named after their concern (`Application/Common/Decorators`: `LoggingDecorator`, `ValidationDecorator`, applied to every `IRequestHandler<,>` by `AddRequestHandlers`); ones written for one interface are named `<Interface without I><Concern>Decorator` (`Infrastructure/Persistence/Decorators`: `UserRepositoryInstrumentationDecorator`, registered by hand in `AddInstrumentationDecorators`). One class per file. What a decorator delegates to stays in a folder named after the concern (`Persistence/Instrumentation/PersistenceInstrumentation`: the meter and logs). The Application folder was `Behaviours` (a MediatR leftover) and the persistence ones were `Instrumented*`; don't bring either name back.
- Validators and handlers are found by assembly scanning (`AddValidatorsFromAssembly`; request and domain event handlers through `FindImplementations` in `Application/DependencyInjection.cs`). Adding a class is enough; nothing needs to be registered by hand.
- **Tables live in named schemas, never in `dbo`** (`Infrastructure/Persistence/Schemas.cs`): `Accounts` for the users domain (`[CqrsApi].[Accounts].[Users]`) and `Messaging` for infrastructure shared by every area (`[Messaging].[OutboxMessages]`, `[Messaging].[OutboxMessageConsumers]`). There is no default schema: every `*Configuration.cs` calls `ToTable(name, Schemas.X)`, and `SchemaTests` fails if a table lands anywhere unexpected. Raw SQL must qualify table names (`[Messaging].[OutboxMessages]` in `OutboxProcessor`): an interpolated value in `FromSql` becomes a parameter, not an identifier. EF's `__EFMigrationsHistory` stays in `dbo` on purpose, because moving it would make existing databases look unmigrated. The shared outbox works because there is one `DbContext`; if the API is split into modules with their own contexts, each module needs its own outbox in its own schema.
- `Users` has a **non-clustered** primary key and a **clustered** index on `CreatedAt` (`UserConfiguration`). Ids are Guid v7, time-ordered in .NET, but SQL Server sorts `uniqueidentifier` by its last bytes, so clustering on them would split pages on every insert. Do the same for new aggregates with Guid ids.
- SQL Server access uses `EnableRetryOnFailure` (3 retries, at most 5 s apart; see `AddPersistence`), so with the database down a request fails after about 20 s. Any future explicit transaction (`BeginTransaction`) must run inside `context.Database.CreateExecutionStrategy().ExecuteAsync(...)`, or EF throws because user-initiated transactions can't be retried. Unique violations (2601/2627) are not transient and are never retried.
- Duplicate email is checked twice on purpose: `ExistsByEmailAsync` is the fast path, and the unique index plus `UniqueConstraintViolationException` covers concurrent requests. When it is hit, EF still logs `fail:` lines for the `DbUpdateException` even though the API answers 409.
- Validation happens twice on purpose: FluentValidation checks the input format in the pipeline, and the entity factory protects the domain invariants.
- **Build settings and packages are central.** `Directory.Build.props` sets `TargetFramework`, `Nullable`, `ImplicitUsings` and `TreatWarningsAsErrors` for every project, so don't repeat them in csproj files. `Directory.Packages.props` (Central Package Management) holds every version. To add a package, add a `<PackageVersion>` there and a `<PackageReference>` **without** `Version` in the project. Warnings fail the build.
- **Code style is part of the build.** `.editorconfig` follows the .NET template and the C# coding conventions, and `EnforceCodeStyleInBuild` is on. Rules at `warning` fail the build: file-scoped namespaces, usings outside the namespace and none unused (IDE0005, which is why `GenerateDocumentationFile` is on with CS1591 suppressed), `readonly` fields, and naming (I-prefixed interfaces, `_camelCase` private fields, PascalCase members/constants, camelCase locals/parameters; IDE1006 must keep its own severity line or naming isn't checked in the build). Whitespace and final newlines are checked by `dotnet format --verify-no-changes`, not by the build. EF Core migrations are excluded as generated code. Review what `dotnet format` "fixes": for CS8618 it made `DbSet<User> Users` nullable. The right fix is `DbSet<User> Users => Set<User>();`.
- **Debuggable code: name what you pass.** This is an example project people step through, so a computed argument or return value goes into a named local first (`var sqlString = sql.ToString(); SqlParameter[] parameters = [..];` then `new SqlCommand(sqlString, connection)` / `AddRange(parameters)`; `var message = new OutboxMessage { .. }; context.OutboxMessages.Add(message);`; `return new Statement(sql, parameters);` instead of an expression-bodied `=> new(..., [..])`). LINQ chains that are worth inspecting are materialized into a typed local (`List<Type> concreteClasses = [.. types.Where(IsConcreteClass)];`; a lazy query shows nothing in the debugger), and long lambdas become named local functions. A collection expression needs an explicit type (`SqlParameter[] x = [..]`), not `var`. Plain property accesses (`statement.Sql`, `ex.Message`), constants and lambdas stay inline.
- **NuGet Audit fails the build** on known vulnerabilities, transitive ones included (NU1901-NU1904 as errors; NU1900 "couldn't fetch audit data" stays a warning so offline builds work). Fix a flagged transitive package by adding a `PackageVersion` for the patched version, not by suppressing the warning.
- **Pinned on purpose** (commented in `Directory.Packages.props`): FluentAssertions **7.2.2** is the last open-source release; 8+ has a commercial license, so don't upgrade it. Don't bring back MediatR (13+ is commercial too); an architecture test forbids it.
- **Security pin:** `CentralPackageTransitivePinningEnabled` is on, so a `PackageVersion` also pins a package that only comes in transitively. `System.Security.Cryptography.Pkcs` is pinned to **10.0.13** because Microsoft.Data.SqlClient 6.1.7 (required by EF Core SqlServer 10) brings a vulnerable 9.0.11. Remove the pin once SqlClient depends on a patched version; NuGet Audit fails the build otherwise.
- Error codes follow `Area.Name` (for example `User.NotFound`, `User.DuplicateEmail`, `General.Unexpected`). They are sent to API clients as the ProblemDetails `type` (except for validation) and in `errorCodes` on **every** problem response, 400s included.
- `Error` keeps the **code** and the input **field** separate (`Error.Validation(code, description, field)`). A 400 `ValidationProblemDetails` groups `errors` by `Field`, and `errorCodes` carries the codes. Never put a property name in `Code`.
- Every FluentValidation rule must call `.WithErrorCode(Errors.<Area>.<Error>.Code)`, reusing the domain error code, so a failure has the same code whether the validator or the entity factory catches it. Validators set `RuleLevelCascadeMode = CascadeMode.Stop` (one error per field). The default FluentValidation codes (`NotEmptyValidator`, ...) must not leak.
- Validation messages are fixed to English in `AddApplication` (`ValidatorOptions.Global.LanguageManager.Culture`). Otherwise they would follow the server's culture.
- `AddControllers` sets `SuppressImplicitRequiredAttributeForNonNullableReferenceTypes = true`. Without it, MVC answers missing/null non-nullable strings itself (different message, no `errorCodes`) before the request reaches the pipeline. Input MVC cannot bind at all (for example malformed JSON) goes through `InvalidRequestResponse.Create` (`InvalidModelStateResponseFactory`). It answers in the same `ValidationProblemDetails` shape with `errorCodes: ["Request.Invalid"]`. `AllowInputFormatterExceptionMessages = false` (in `AddPresentation`) replaces the JSON parser's messages, which can name internal types, with "The input was not valid." under the JSON path.
- **Every error response is ProblemDetails with `errorCodes`, even the ones the framework raises.** Request-level codes live in `Api/Common/Errors/RequestErrors.cs` (`Request.Invalid`, `Request.Unauthorized`, `Request.Forbidden`, `Request.NotFound`, `Request.MethodNotAllowed`, `Request.UnsupportedMediaType`, mapped from the status code by `ForStatusCode`). They reach responses through two hooks: `CqrsApiExampleProblemDetailsFactory` (MVC-produced problems such as 415) and `AddProblemDetails(CustomizeProblemDetails)` + `app.UseStatusCodePages()`, which give empty routing and authentication responses (unknown route 404, 405 with its `Allow` header, 401 from the bearer challenge) a ProblemDetails body. Application errors (`User.*`) always take precedence. `Request.NotFound` means "no such route"; `User.NotFound` means "the route exists, the user doesn't".
- Don't put `[Produces("application/json")]` on controllers: it overrides the content type of every result, so error responses would stop being `application/problem+json`. Document response types with `[ProducesResponseType<T>(status)]`, adding `"application/problem+json"` for error statuses.
- Routes with ids use constraints (`{id:guid}`) and typed parameters. A non-GUID id therefore gets a 404 `Request.NotFound` from routing, and `Guid.Empty` gets a 400 `User.InvalidId` from the validator.
- Time comes from the built-in `TimeProvider` (registered as `TimeProvider.System`). Don't reintroduce a custom date provider.
- The project was refactored in stages: persistence-ignorant domain, own `Result<T>`, unit of work and migrations, CQRS read side, error handling and validation codes, domain events, API, build hygiene, tests, SQL Server + Docker, consistent framework-level errors and SQL retries, the transactional outbox, and the removal of MediatR (own handlers and decorators). The git history was squashed into a single commit before the repository went public, so the stages are no longer in git.
- In Development, EF's SQL command log (`Microsoft.EntityFrameworkCore.Database.Command`) is at `Warning` in `appsettings.Development.json`, because the outbox polls every 2 s and would flood the log. Set it to `Information` temporarily to see the SQL.

## Tests

One test project per layer, and each references **only** the layer it tests. A test that needs another layer belongs to a different project. Shared settings and packages (xUnit, FluentAssertions, Microsoft.NET.Test.Sdk, coverlet, `using Xunit`) are in `tests/Directory.Build.props`.

|---|---|---|
| `CqrsApiExample.Domain.UnitTests` | CqrsApiExample.Domain | entity invariants, equality, domain events, `Result<T>` |
| `CqrsApiExample.Application.UnitTests` | CqrsApiExample.Application | handlers (mocked `IUserRepository`/`IUnitOfWork`/`IUserQueries`), validators, decorators (with a stub inner handler); `RequestPipelineTests` and `Events/` build the real registration with `AddApplication()` (`ValidateOnBuild`) to prove every handler sits behind logging → validation |
| `CqrsApiExample.Infrastructure.IntegrationTests` | CqrsApiExample.Infrastructure | real SQL Server (Testcontainers), one database per test with migrations applied: mapping, unique index (2601/2627 translation), interceptor, unit of work writing the outbox, `OutboxProcessor` (backoff, dead letter, per-handler idempotency, expired leases, two processors never sharing a message; the clock is a controllable `TestClock`), read-side projections; the same scenarios for the ADO.NET provider (`AdoPersistenceContract`, run once per `AdoWriteMode` by `AdoPersistenceTests` and `AdoCommandPerStatementPersistenceTests`; rows are read back through EF to prove both agree on the schema), the provider flag in DI and the instrumentation (`FakeLogger`, `MetricCollector`) |

- Integration tests need **Docker**. `tests/Shared/SqlServerFixture.cs` (linked into both integration projects with `<Compile Include=... Link=...>`) starts one SQL Server container per test assembly through an xUnit collection fixture, and hands out a **new database per caller** (`CreateDatabaseConnectionString()`). Test classes must be in that collection (`[Collection(SqlServerCollection.Name)]` / `[Collection(ApiCollection.Name)]`), otherwise they get no container.
- `ApiFixture` owns the container plus one shared `ApiFactory`. Tests that need different services call `api.CreateFactory(services => ...)` (see `UnexpectedErrorTests`), which gets its own database. `ApiFactory` replaces `IEmailSender` with `FakeEmailSender`. Protected endpoints need a token: `factory.CreateAuthenticatedClient()` issues one through the API's own `IAccessTokenIssuer` (no registration or login); `AuthEndpointsContract` covers the real register → login → call flow and every invalid-token case, once per provider. Tests in the shared API also share its database, so use unique emails (`NewEmail()`).
- `Program` is `public` only so `WebApplicationFactory<Program>` can see it.
- When adding a layer rule, prove it can fail: introduce the violation temporarily and see the test go red.
- Log assertions use `FakeLogger<T>`/`FakeLogCollector` (Microsoft.Extensions.Diagnostics.Testing).
- Test names follow `Method_Should_Behavior` / `Method_Returns_X`, with Arrange/Act/Assert comments.
